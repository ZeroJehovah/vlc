# 暂停恢复日志分析（2026-11-04）

这是脱敏后的技术摘录，不包含用户视频名称、媒体地址、完整设备指纹或应用设置。输入为用户的 `pause-diag2` 日志；手机 Android 13 / API 33，AudioTrack 输出、48kHz 双声道 PCM、1 倍速。

## 日志直接证明的链条

记录到两次暂停恢复。第一次恢复的首个同步偏差约 172.3ms，未达到稳定版 180ms 清空阈值，随后采用重采样修正。

第二次恢复：

| 事件 | 记录 |
| --- | --- |
| AudioTrack 恢复调用耗时 | 32,885µs |
| 解码器恢复完成到首个新音频块 | 88,539µs |
| 同步查询的输出排队延迟 | 1,951,624µs |
| 音频偏晚 | 216,818µs |
| 触发修正 | `flush_late`，超出 `3 × AOUT_MAX_PTS_DELAY = 180,000µs` |
| 清空输出耗时 | 1,679µs |
| 下一轮同步偏差 | −1,727,730µs |
| 接着执行的修正 | `insert_silence`，插入 1,727,730µs、82,931 帧静音 |

因此，日志确认 VLC 清空了已经排队的音频，然后主动补入约 **1.73 秒静音**。这足以解释一次明显的声音中断，但还不能单凭日志确定最初的所有延迟来源。

第一次恢复的新解码数据在解码器恢复完成约 178.7ms 后才到达。两次恢复调用本身约 33–34ms，不能将整段静音都归于 Android 的 `play()` 耗时。

## 源码和回归测试证明的缺陷

`modules/audio_output/audiotrack.c` 的发送线程会在 `b_thread_paused` 为真时等待 `thread_cond`。旧 `Pause(false)` 清除暂停状态并调用 Android `play()`，却没有通知该条件变量。

因此，即使循环队列已经有音频，线程仍可能等到下一次 `Play()` 投递数据等操作发出信号后才运行。修复是在恢复路径加 `vlc_cond_signal()`；状态更新和通知都在现有互斥锁内完成。增加的时间戳只用于诊断首次发送的等待时间。

测试直接编译实际 AudioTrack 源码，使用实际 `AudioTrack_Thread()` / `Pause()`，仅模拟 JNI 和 VLC 的宿主运行环境。旧源码会停在已排队的 200ms PCM 上；修复后 20 次均能在没有新解码输入的条件下发出全部 38,400 字节 / 9,600 帧，ASan/UBSan 通过。

## 尚未证实

- 缺失唤醒是否是本手机同步偏差超过阈值的主要原因，需要新版日志验证。
- 本修复针对 AudioTrack，不能直接解释或保证解决此前 AAudio 的卡顿。
- Android 输出路由和用户所测 4.x 精确版本尚未确定。
- 当前稳定 AudioTrack 源码的 `AUDIOTRACK_HW_LATENCY` 未启用，不能把“旧硬件时间戳未更新”作为已证实原因。
- 此前日志中较早的日志服务异常，不能当作当前诊断版播放过程中新发生的错误。

没有修改同步阈值、没有加入暂停恢复宽限期，也没有迁移 VLC 4 的统一音频主时钟。接下来以手机实测为准，比较发送线程唤醒耗时、首块音频偏差及是否继续出现清空后补静音。

## resume-fix1 真机结果

用户在蓝牙耳机 EDIFIER Lolli Pods Plus 上复测后仍能听到卡顿。两次恢复中，发送线程的唤醒延迟分别为 **50µs 和 108µs**，说明唤醒修复有效，但不足以解决同步误判。

第一次恢复后，一次标为 `WRITE_NON_BLOCKING` 的 AudioTrack 写入实际耗时 **383,827µs**。下一次同步查询得到约 342ms 正漂移并执行 `flush_late`，随后插入 **1,771,734µs** 静音。第二次恢复的首个同步点已有约 361ms 正漂移并清空输出，随后插入 **1,544,490µs** 静音。

这组结果把范围缩小到 Android/厂商 AudioTrack 的恢复写入和核心的单次延迟判断。resume-fix2 在进入 API 23 非阻塞写入前检查内部缓冲的待播放帧，缓冲已满时直接等待，避免带着满缓冲调用 Java；超过 50ms 的写入会记录耗时。同步阈值和清空/补静音规则暂不改动，先用真机结果确认写入阻塞是否消失。

## resume-fix2 真机结果

用户在同一蓝牙耳机上继续复测，并确认只有声音卡顿、视频画面继续播放。新版日志中没有出现 `[pause-fix] nonblocking_write blocked_us=`，说明满缓冲保护避开了此前的厂商写入阻塞。

第一次恢复的发送线程唤醒延迟为 **384µs**，首个音频块只偏差约 12ms；约 324ms 后播放头估时出现一次 `timing screwed, reset positions`，下一次查询判断偏晚约 316ms。第二次恢复的首批样本约为 88–110ms，随后一次约 489ms 的解码间隔又让估时失效，下一次判断攀升到约 486ms。

两个周期仍按原规则清空音频，并分别补入 **1,731,191µs** 和 **1,618,963µs** 静音。视频线程和渲染记录持续运行，所以这是 VLC 3 输入主时钟下对音频瞬态的过度纠偏，不是蓝牙链路整体停顿。

resume-fix3 因此改变核心恢复策略：暂停恢复后的短窗口内，输出估时暂时失真时保留排队音频，并使用已有重采样器逐步收敛；显式 flush、seek 或输出重启仍退出恢复状态。输出连续稳定四批且超过正常准备时间后结束恢复，之后继续使用原有同步规则。真机效果仍待验证。

## resume-fix3 真机结果

2026-11-04，用户在同一台 Redmi K50 Ultra / Android 13 和同一蓝牙耳机上测试 `3.7.2-resume-fix3`，共执行四次暂停恢复。主观结果显示此前约一秒的声音中断没有再次出现，蓝牙固有延迟与此前正常播放没有明显区别；音画同步只做了初步感受，尚未用稳定口型画面逐次核对。

日志确认新路径实际生效：四次恢复均没有 `flush_late`、`insert_silence` 或 `defer_silence_resume`。发送线程唤醒延迟为 **164–620µs**，后端恢复调用耗时 **48,644–196,310µs**。第一次恢复在 2.076 秒后正常结束恢复状态，结束偏差约 **20.392ms**。

后三次恢复仍出现了播放头估时跳变，但新的保护逻辑保留了音频。第二次和第三次开始时偏晚约 590–599ms，后续 `timing screwed` 停止了原有重采样状态；在用户下一次暂停前，估时偏差分别缓慢降到约 561ms 和 573ms。第四次从约 504ms 降到 434ms。可见连续声音已经恢复，但重采样收敛远慢于一次日常暂停后的可接受音画同步窗口，因此不能把“没有卡顿”等同于“同步已经完全归零”。这些是 VLC 对 AudioTrack 的估时偏差读数，是否表现为实际口型和声音错位仍需主观确认。

resume-fix3 因此只能算部分修复：它消除了明显的断音，但没有保证音画同步。

## resume-fix3 后续音画不同步反馈

用户进一步测试后确认，至少有一个场景出现**严重音画不同步**，同时没有报告原先约一秒的断音。这与日志中 500–600ms 的持续估时偏差一致，因此不能继续把“听不到卡顿”当作修复完成。

同一日志还证明音频生产路径会被后端阻塞：第二次恢复后一次 `backend_play` 实际耗时 **581.691ms**，第三次为 **566.325ms**。这里的 `backend_play` 是 VLC 向音频输出投递已解码 PCM 的调用，不是视频线程。恢复时软件环形队列已接近 2 秒上限（`queued_us=1,982,104`）；发送线程未释放空间时，生产调用只能等待。视频路径不受这把锁影响，继续推进，于是形成“视频不卡、音频队列落后”的条件。

fix3 的恢复路径还在持有 `p_sys->lock` 时调用 Android `AudioTrack.play()`，发送线程也可能在持有同一把锁时等待内部缓冲空间或调用厂商 `write()`。旧日志足以证明生产锁上的数百毫秒阻塞，但仅凭现有标记不能把每一次 `backend_play` 停顿唯一归因于 `play()` 或 `write()` 中的哪一个 Java 调用，因此这两条路径都需要解耦。

## resume-fix4 实现与验证边界

fix4 保留 fix3 的非破坏同步恢复，并针对上述阻塞重构 AudioTrack API 23 路径：

1. 发送线程在 `p_sys->lock` 内只把一块 PCM 从 Java 环形数组复制到私有 staging 内存，随后推进 `circular.i_read` 并释放生产锁。
2. 可能阻塞的 `SetByteArrayRegion()` / `AudioTrack.write(WRITE_NON_BLOCKING)` 在 `p_sys->lock` 外执行。
3. 独立 `write_lock` 串行化 `play()`、`pause()`、`flush()` 和 `write()`，防止 Java 音频状态调用互相穿插。
4. `b_backend_paused` 保证恢复调用完成前不重新写音频；flush 通过 generation 使已暂存旧数据失效。
5. `i_samples_inflight` 把尚未被 AudioTrack 接受的 staging 帧计入时间估算，避免提前误判队列为空。

回归测试让模拟厂商 `write()` 故意阻塞 150ms：fix3 源码会让 PCM 生产调用全程等待，fix4 源码可在阻塞期间完成下一次入队。第二次回归让厂商只接受 partial write，并在 staging 仍非空时请求停止，确认发送线程能在 1 秒内退出，不会因为等待写锁而空转。两组测试均通过 ASan/UBSan；原有暂停唤醒的 20 次负对照/修复对照、实际 `aout_DecSynchronize()` 恢复决策测试也继续通过。Release 构建、lint、签名升级身份和 APK 标记检查均通过。

这些测试证明锁和 staging 的行为，不证明手机的蓝牙 AudioTrack 厂商栈已经完全恢复。fix4 仍需真机观察：若仍有 `staged_write blocked_us`，说明厂商调用本身仍阻塞；只有当它不再同步拖住 `backend_play`，并且口型测试也正常，才能确认这条因果链被切断。
